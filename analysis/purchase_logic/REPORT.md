# 购买逻辑、延迟控制与图文识别深挖

日期：2026-11-02。对象：当前已恢复的 S11赛季末 宏及对应原生程序。

## 结论先读

这套逻辑的核心是：**预筛选/收藏 → 局部 OCR 监视倒计时 → 两秒窗口进入购买 → 分段计时补偿及本机改时 → 鼠标点击 → OCR 读取结果 → 小步修正下一次延迟**。

不是从已解析宏中发现了某个 HTTP 下单接口，也不是图像模型直接识别枪皮并决定购买。业务决策主要是显式条件分支、文字匹配、找色、坐标点击和固定规则。原生程序仍包含其他网络能力，不能据此推断整个 EXE 没有网络请求。

最重要的新发现：**原始动作数组按存储顺序呈现，加载器会将每一层动作列表倒序还原。** 直接从旧版 actions.readable.txt 顶部往下解释执行，会把“读取 → 判断”读成“判断 → 读取”，把“移动 → 点击”读反。旧文件作为原始存储结构仍然正确，但不是执行顺序。

本次没有启动 EXE、没有执行宏、没有点击购买、没有调整系统时间、没有访问内置服务。

## 证据等级与阅读方法

- **直接证据**：恢复宏的表达式、参数、分支及启用状态；原生反编译与机器码。
- **交叉证据**：固定提交的 Quickinput 上游实现与原生函数的结构相符；不把上游全部代码当作私有分支源码。
- **推断/待验证**：实际运行时间、真实窗口视觉、服务器接收时刻、识别准确率、成功率。未通过实机运行证明。

附带 actions.execution_order.json / .txt 按加载器顺序展开，但仍是**静态控制流树**，不是一次运行轨迹。next / next2 未交换；循环、跳转、子程序定义和调用仍需结合阅读。source_path 指向原始 macro.readable.json 的数组下标。

共保留 2,281 个动作；考虑禁用祖先后，有 142 个禁用节点。37 个 OCR 节点中 31 个未禁用；39 个找色节点均未被禁用。这些数量不是一次购买执行的次数，“未禁用”也不证明节点一定可达。

## 一、动作顺序的原生证据

文件 native_recovered/decompiled/b3790.c 中，加载器：

1. 从 param_2[1]（输入数组尾部）开始。
2. 读取 lVar7 - 0x48 位置的前一个 TypePack 元素。
3. 解码动作后追加到输出数组尾部。
4. 执行 lVar7 = lVar7 - 0x48，直到输入起点。

机器码中还能看到不同动作加载分支及宏加载分支调用同一函数，例如 RVA 0x92bd2、0x92cce、0x127306。相关反汇编保存在 evidence/native/loader_order.asm。

因此只倒序动作列表：actionsEntry、actions、actionsEnding、next、next2。**不能倒序 rect 坐标、脚本内语句、字符串或参数。**

本次新工具 analyze_purchase_logic.py 输出带原始路径、继承禁用状态的加载顺序；3 项单元测试检查递归倒序、原数据不变、坐标与脚本不变、禁用继承和完整动作数量。

## 二、购买主流程

### 1. 初始状态与预筛选

加载顺序首先处理动态参数同步、状态显示、数量初始化等，再调用“时间校准”子程序 id=7；之后进入自动收藏/候选筛选与主循环。普通 block 是供调用的定义，不能把其定义位置理解成直接执行位置。

恢复的初始化脚本 recovered_source/scripts/0001.txt 明确给出：

| 参数 | 初始化脚本值 |
|---|---:|
| 购买延迟 | 840 ms |
| 动态延迟 | true |
| 连续点击 | true |
| 点击间隔 | 3 ms |
| 自动收藏 | true |
| 刷新界面 | false |
| 跳过成功页 | true |

QIML 中有不同的控件默认值，例如点击间隔为 30、动态延迟勾选为 0。**不能只看 UI 默认值判断本次保存配置，更不能据此断言真实启动后的最终值**；还需考虑配置加载及同步顺序。

自动收藏阶段逐项读取“枪名设置栏、启用、价格上下限、成色、磨损度”等配置。列表有四个价格识别区域；子程序 id=3 清理 price 后，价格高于上限或 price<=0.5 会跳出相应流程；id=6 只有在最低价格<=price<=最高价格且 CSZ<=磨损度时调用添加子程序 id=4。id=13 负责磨损识别及相关分支。

特别注意：**两秒抢购分支中的 Qprice、Qname、QCS 主要服务后续识别/归类/计数。** 该分支实际点击早于“抢购信息判断”节点，因此不能把后置识别误认为一次新的成交前价格复核。已有预筛选不等于对最终订单做了原子条件校验。

### 2. 倒计时触发

主循环用 OCR 读取 time_countdown。关键区域为 [8160,8060,9045,8340]。

- 精确等于“0分2秒后解锁购买”：进入主购买分支。
- 精确等于“0分1秒后解锁购买”或“0分0秒后解锁购买”：跳转 id=22，属于另一条控制流，不是继续执行同一个两秒准备流程。
- “0分5秒/11秒/16秒后解锁购买”：在刷新条件分支里调用 id=11。
- “应用外观”：走成功页处理、计数、截图和后续操作。

这是基于 OCR 字符串的状态机，不是读取游戏内存中精确的服务器倒计时。

### 3. 两秒分支的真实顺序

原始入口：$.actions[0].next[0].next[3]。该分支有 40 个直接子节点，以下省略部分显示/统计动作：

1. 读取 time_ms()、time_s()，记录 time_start=time_rms()。
2. OCR 读取余额、价格，更新余额相关状态。
3. 移动到购买入口附近，等待 30 ms，点击，再等 30 ms，移动到确认区域附近。
4. 记录准备结束时刻 time_end，执行第一段等待补偿。
5. 记录 time_starto；按 setmsa 条件选择异步改时路径。
6. OCR 读取枪名和成色/磨损；找色决定使用哪个成色区域，必要时读“极品”标记 JYP。
7. 补足识别阶段时间，再按购买延迟和改时耗时继续等待。
8. 按分支同步修改本机时间，最后补偿到目标点击时刻。
9. 单击；若连续点击开启，进入标称 100 ms 的重复点击窗口。
10. 进入标称 3,000 ms 的反馈识别循环，识别结果并调整下一次购买延迟。
11. 调用 time_set_ms(time_ntp_ms()+1)，然后检查计时误差、进行商品信息归类，置 time_countdown 为“等待中”。

这里的 timer 是有时间上限的循环结构，不是简单“先 sleep 这么久”。其内的 OCR 或其他阻塞操作仍可能让退出时刻超过名义上限。连续点击的 3 ms 也是参数，不是经实测保证的点击周期。

## 三、延迟控制拆解

令 D=购买延迟，C=set_o，U=time_starto。以下公式直接来自脚本。

### 1. 第一阶段：扣除准备耗时与当前秒内偏移

```text
time_t1 = time_end - time_start
time_m_s = time_millisecond - time_second
sleep(1500 - time_t1 - time_m_s)
```

目的不是每次固定等待 1,500 ms，而是把前面 OCR、移动、点击等开销及触发时秒内偏移扣掉。证据：action_scripts/0103_script.txt。

### 2. 第二阶段：OCR 开销归一化

```text
time_dep = time_rms() - U
sleep(400 - time_dep)
if time_dep > 400:
    sleep(D + 300 - C - time_dep)
else:
    sleep(D - 100 - C)
```

在没有超时、负等待等情况时，两条路径都试图让改时前的进度接近 U+D+300-C。证据：action_scripts/0100_script.txt 及其相邻分支。

### 3. 改时和最终对齐

同步路径会执行：

```text
time_set_ms(time_second + 3000)
time_endo = time_rms()
time_t2 = time_endo - U
sleep(D + 500 - time_t2)
time_check = time_rms()
time_check_tip = time_check - U - 500
```

理想情况下，点击起点约为 **U+D+500 ms**，time_check_tip 接近 D。D=840 时，是第二阶段起点后约 1,340 ms，而不是“看到可购买后 sleep 840 ms”。这只是控制目标，不能保证真实点击误差或服务器接收时刻。

time_set_msa(time_ms()+1000) 为另一条异步改时路径；初始化校准测得 C>D-100 时会将 setmsa 置真。原生回调创建并分离工作线程，线程再调用同一个改时辅助函数。

### 4. 这确实涉及本机时间，而不是普通变量赋值

证据链：

- 脚本绑定 time_set_ms → 构造器 RVA 0x18c1f0 → 虚表 0x1429f0ec0 → 回调 RVA 0x17c610 → 辅助函数 RVA 0x177a30。
- time_set_msa → 构造器 RVA 0x18c290 → 虚表 0x1429f10d8 → 回调 RVA 0x17c870 → 工作线程 RVA 0x191a00 → 同一辅助函数。
- 0x177a30 使用 `msec*10000 + 0x019DB1DED53E8000` 转换时间，再调用两个系统入口，并返回耗时或 -1。
- 固定上游 source/src/scriptinterpreter.cpp 的 SetSystemTime_UnixMs 在公式、调用顺序和返回值上相符，明确使用 FileTimeToSystemTime、SetSystemTime。

结论：**这是系统改时逻辑的强交叉证据。** 原生 IAT 中上述两个调用目标仍经过未完全还原的入口，不能把 API 名称描述成已由原生导入表独立确认。实际改时是否成功取决于权限和返回值，本次没有执行验证。宏调用没有检查这些改时返回值。

time_rms 的原生回调只读取另一计时入口；上游对应 clock()。因此脚本区分了系统墙钟与运行耗时计时，并非所有 time_* 都是同一种时钟。

### 5. 动态反馈：规则步进，不是 PID 或学习模型

反馈区域 [4163,1297,5841,2409] 识别为 feedback；先清空、OCR、查找关键词，再依次判断。命中处理后跳出当前反馈循环。

| 关键词 | 条件 | 延迟更新 | 保存脚本中的步长 |
|---|---|---|---:|
| 尚未开放 | feedback_1>0 | D -= fd1 | 0 |
| 在公示期 | feedback_2>0 | D += fd2 | 1 |
| 玩家名单 | feedback_3>0 | 不变，视为已进池 | — |
| 队列已满 | feedback_4>0 | D -= fd4 | 1 |
| 被购买 | feedback_5>0 | D -= fd5 | 0 |
| 玩家过多 | feedback_6>0 | D -= fd6 | 1 |

修改还要求动态延迟开启及对应 fd11/fd22/fd44/fd55/fd66 开关为真。这些单项开关在保存初始化脚本中均为 1。另有“抢购玩家”的直接 OCR 分支将状态视为已进池。

不要将“尚未开放”的减法擅自改读成加法；原脚本确实如此。本样本 fd1=0，所以默认对此类反馈没有实际改动。

旧的固定 ±1 调整与跳过抽奖页流程位于已禁用的祖先分支下；不是当前启用路径。名为“自动延迟”的 block id=12 虽有统计表达式，但没有找到任何 blockExec id=12 调用，不能把它说成当前正在运行的智能估计器。

## 四、图文识别拆解

### 1. OCR 模型与找色各做什么

恢复资源中存在：

| 资源 | 角色 | 大小 |
|---|---|---:|
| resource_02.bin / OCR_DET | 文字检测模型 | 4,729,474 字节 |
| resource_03.txt / OCR_KEY | 字符字典，6,623 行 | 26,250 字节 |
| resource_04.bin / OCR_REC | 文字识别模型 | 10,812,334 字节 |

模型内部含 PaddlePaddle Graph 字符串；识别模型还含 Softmax 节点。上游接口链接 ONNX Runtime 与 qiocr。可以确认它是检测/识别/字典这一类 OCR 管线；**不能仅凭这些认定具体 PP-OCR 版本、精度、量化方式或 GPU 配置。**

本宏没有图像模板匹配动作节点；“图”的判断主要是 39 个区域找色节点。“枪名/系列识别”主要读取文字，再用字符串和硬编码条件映射，并不是训练出的枪皮图像分类器。

### 2. 关键区域

坐标采用 0..10000 的归一化范围，不是屏幕像素。上游转换在完整范围内近似为 x/10000*宽、y/10000*高；窗口模式及自定义范围会改变对应位置。

| 用途 | 变量 | 区域 [左,上,右,下] |
|---|---|---|
| 倒计时 | time_countdown | [8160,8060,9045,8340] |
| 价格 | Qprice | [3410,3650,3838,3960] |
| 枪名 | Qname | [3074,3382,4750,3790] |
| 成色分支 A | QCS | [4226,5106,4971,5393] |
| 成色分支 B | QCS | [4247,4309,4960,4596] |
| 极品标记 | JYP | [4669,4698,4960,4976] |
| 余额/存量 | sjb存量 | [8820,370,9421,602] |
| 购买反馈 | feedback | [4163,1297,5841,2409] |
| 进池文字 | 无变量 | [8104,8498,9144,8797] |

完整 37 个区域见 ocr_regions.csv，包含继承禁用状态和原始节点路径。

### 3. row、match 不能混淆

字段映射：0e82f4bb → row，53853f41 → match。

- 上游 OCR 调用将 row 传给 skipDet 参数，表示跳过文本检测阶段的识别路径，不是“要求文字精确匹配”。价格识别开启了 row。
- match=true 才是整个识别字符串相等；否则使用子串包含判断。
- 在普通、非多目标路径下，先把识别文字写入变量，再比较匹配文本。因此 time_countdown 节点虽附带匹配“时”，识别出秒级文本后仍可先更新变量，由后续独立条件使用。
- 若区域没有图像或未识别到文字，上游走 next2，未见统一清空所有目标变量的动作。feedback 有显式重置，但其他变量可能沿用旧值；私有实现是否完全一致仍需动态验证。

### 4. 识别后处理

价格：rmc(price) / rmc(Qprice)。磨损：rms(QCS) → 截取前 7 个字符 → O/o 替换为 0 → 在索引 1 插入小数点。成色 S/A/B/C 用 find 查找；枪名从连字符和前缀拆分，再进入硬编码的系列/型号归类。

按上游语义，单参数 rmc/rms 只保留数字，而不是一般的格式校验。因而：

- 12.34 可能被清理成 1234，不能把清理函数当成严格金额解析器。
- 若 O/o 在“只保留数字”阶段已删除，后续 O→0 无法补回丢失位数；这段纠错的顺序值得复核。
- 倒计时条件是精确字符串，空格、漏字或错字可能错过两秒触发。

## 五、值得优先验证的风险

1. **执行顺序误读已解决**：以前的数组转储不是加载后顺序；新文件同时保留原始 source_path。
2. **反馈 find>0 疑点**：上游 find 从 0 计数，未命中返回 -1；若关键词就在开头，返回 0，当前条件将漏判。宏中的其他成色判断使用 >=0，也支持这是待检查的不一致。未做原生解释器运行实验，不把它写成已复现故障。
3. **延迟误差符号**：time_check_t2 = D-time_check_tip，仅检查 >5。迟到意味着 time_check_tip>D，结果为负，反而不触发此提示；且该检查在反馈修正 D 之后，可能混入下一次参数。
4. **未见调整限幅**：当前增减表达式未对 D 做显式上下限裁剪；UI 范围是否还会约束脚本赋值未证实。OCR/改时耗时过大还会使 sleep 参数变为负数，实际行为需要运行库语义确认，不能按理想公式继续推断。
5. **改时失败与恢复**：宏没有核查改时函数返回值；中断、NTP失败或异步竞争时是否恢复本机时间，需要单独验证。不能把 time_set_* 当作无副作用的局部变量操作。
6. **没有一处通用的临点复核**：当前两秒分支的详细商品归类位于点击后。应区分预筛选、点击动作与实际成交，不能声称保证价格/数量条件原子成立。
7. **识别质量未评估**：没有实屏样本与人工标签，无法给识别率、成功率或最佳延迟参数。
